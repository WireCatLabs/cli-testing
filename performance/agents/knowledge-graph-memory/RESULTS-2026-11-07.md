# Memory for AI agents: results so far (7 November 2026, in progress)

Why this was run: WireCat wants to be the local personal context for AI agents. The question is whether an agent
answers questions about a person's records better with WireCat Memo, with a third-party memory engine (Supermemory,
Mem0, Hindsight, Honcho), or with the records as plain files. All data is synthetic: a year of a made-up team's
chat, mail, notes and meeting notes, with 50 questions whose answers are known.

This page collects the results while the round runs. Numbers marked *pending* are still running. The full method
and the earlier rounds are in [README.md](README.md) and [RESULTS.md](RESULTS.md).

## Where this stands (8 November 2026, morning UTC)

**With an agent, WireCat Memo leads this set.** OpenClaw + WireCat answers 50 of 50 and cites the right record in 46,
for the lowest cost ($1.92); Hermes + WireCat answers 49 for ~$1.49 (section 4). Engines that keep a model's summary
instead of the records lose facts (Supermemory: its agents answer 18 and 19 of 50) or the source (Honcho answers 50
but cites the right record in 4). The same agent with the records as plain files also answers 50 of 50, so on this
set memory buys cost, speed and a cited source, not accuracy. The set was built by us, 50 questions, and the engines
ran on their defaults; Mem0 and Cognee could not be measured.

**Where Memo is behind: search alone on questions worded unlike their record.** Of the 17 such questions, Memo puts
the record in its first 10 for 0.53, Supermemory 0.88, Honcho 0.76, Letta 0.65 (section 2). Every cause was measured
([meaning-loss](meaning-loss/README.md), section 3):

| Cause | 17 reworded, @10 | State |
|---|---|---|
| The benchmark gave every mail one fixed sender and its id as subject, which Memo embeds; other engines got the text alone | 0.48 → 0.53 | fixed in [memo_baseline.py](memo_baseline.py) |
| `search all` filled its top 10 turn by turn from each source, so weak notes pushed out strong mails | 0.53 → 0.62, with the next row | merged, [cli-core #2665](https://github.com/WireCatLabs/cli-core/pull/2665); release 0.609.0 in progress |
| Mail was searched by meaning with another question text than notes, so their scores did not compare | in the row above | merged, #2665 |
| After that fix, hits found only by words sank under every hit found by meaning (74 of 460 top-10 places → 15) | 0.62 → 0.59, exact-word hits back to 92 of 460 | [cli-core #2667](https://github.com/WireCatLabs/cli-core/pull/2667), open |
| The model: e5-small alone finds 0.71, EmbeddingGemma 300M alone 0.94, above every hosted engine | not yet measured inside Memo | model setting merged ([cli-core #2608](https://github.com/WireCatLabs/cli-core/pull/2608)); Memo using it: [cli-memo #676](https://github.com/WireCatLabs/cli-memo/pull/676), open |
| With no model downloaded, a question holding "HH:MM" found nothing and said nothing | (all questions) | merged, [cli-core #2657](https://github.com/WireCatLabs/cli-core/pull/2657) |

The #2665 and #2667 numbers come from a patched copy of memo 0.131.50, not from a released build; they are measured
again once memo ships with them.

## Datasets

| Set | Records | Questions | What it tests |
|---|---:|---:|---|
| v2, 10K | 10,000 | 50: five kinds, each asked about ten projects | current and original date, owner, commitment, an unrecorded budget |
| v3 | 10,444 (the v2 records unchanged, 444 added) | 50 of 21 kinds, 2 or 3 each | money (price after a revision, partial payments, balance, refund, who paid), calendar (moved meeting with time, time zone, relative date, cancelled, cancelled then back on, new weekday), people and decisions, unrecorded answers |
| v3, other words | the same 10,444 | the same 50; 18 reworded so they share no phrase with the record ("rented servers" for "hosting agreement") | search by meaning, not by the record's words |

Built with wcatbench (`wcatbench dataset build synthetic -p records=10000 -p version=3`, add `-p paraphrase=1` for
the reworded set).

Hindsight on the reworded set, all 46 as typed: 0.30 / 0.66 / 0.78, against 0.83 at @10 with the record's words.

Honcho by family, @5: money 1.00, calendar 0.94, people and decisions 0.39. Word search: 0.64, 0.69, 0.71.

Until 8 November the benchmark gave every mail it loads into Memo the sender "Synthetic Sender" and its record
id as subject (memo_baseline.py). Memo embeds a mail's sender and subject with its text, so that one fixed line
sat in every mail's vector; the other engines got the record text alone. Each mail now takes its subject and
sender from its own text ("Subject. Name: body", 3,970 of 4,372 mails name the writer). The rows marked "own
subject and sender" use it; the agent runs in section 4 still used the old headers.

Six Memo 0.131.47 "question as typed" replies were empty because of a bug: a query with a colon ("HH:MM") returns
nothing ([cli-memo #674](https://github.com/WireCatLabs/cli-memo/issues/674)). Memo 0.131.50 fixed it when a model
is downloaded, which is where "as typed" rose from 0.71 to 0.88 at @10. With no model, word search alone still
returns nothing for the same six questions (q14 to q19), so #674 is open again.

Supermemory's numbers are its hybrid search over documents, which is not what its agent plugins read: they search
its memories only, and on 10K it kept 1,585 memories for 10,051 documents (README, FIND-2311).

What it showed: once the words differ, word search collapses and Memo almost does too. Plain meaning search
(Letta, no rewriting) keeps 0.65, and Honcho holds best because a model rewrote every record into conclusions at
write time (paid, slow, and the records go to OpenAI).

### Memo over records rewritten at write time

[enrich_records.py](enrich_records.py) added standalone facts and two questions in other words under each record's
own text (gpt-4o-mini, $0.60 for 10,444 records, 45 min). The record keeps its name, so a hit still cites it.

| Memo 0.131.47, e5-small | Plain records | Rewritten records |
|---|---|---|
| all 46, question as typed, @1 / @5 / @10 | 0.24 / 0.63 / 0.71 | 0.35 / 0.69 / 0.72 |
| all 46, words joined by OR, @1 / @5 / @10 | 0.45 / 0.79 / 0.87 | 0.39 / 0.89 / 0.91 |
| 17 reworded, other words, as typed, @10 | 0.34 | **0.56** |
| 17 reworded, other words, OR, @10 | 0.36 | **0.53** |

What it showed: rewriting closes about half of the gap to Honcho (0.76) on reworded questions and keeps the
source, for $0.60 per 10,000 records. The gain comes through memo's word search: meaning search alone over the
rewritten records finds 0.67, a little less than over the plain records (0.71), I think because the added text
dilutes each record's vector.

## 3. Meaning search alone, model against model

[eval_embeddings.py](eval_embeddings.py): vectors only, no word search, no store, on this machine. Same v3 records
and questions.

| Model | Licence | All 46, @5 / @10 | 17 reworded, record's words, @10 | 17 reworded, other words, @10 | Index time, 10,444 records |
|---|---|---|---:|---:|---:|
| multilingual-e5-small (full precision; Memo ships it 8-bit) | MIT | 0.89 / 0.91 | 1.00 | **0.71** | 93 s |
| multilingual-e5-small over the rewritten records | MIT | 0.91 / 0.91 | 1.00 | 0.67 | 316 s |
| multilingual-e5-large | MIT | 0.88 / 0.93 | 1.00 | **0.82** | 1,368 s |
| Qwen3-Embedding-0.6B (quantized, fastembed's `Qwen/Qwen3-Embedding-0.6B-Q`) | Apache-2.0 | 0.71 / 0.80 | 0.94 | 0.50 | 2,694 s |
| EmbeddingGemma 300M | Gemma Terms | **0.91** / **0.93** | 1.00 | **0.94** | 505 s |

Qwen3-Embedding-0.6B in its 8-bit form came out below e5-small on every column and took 29 times as long to
index. I used the query instruction its model card gives and fastembed's own pooling for it; I did not try the
full-precision model (2.4 GB), so the loss may be the quantization, not the model.

What it showed: the same e5-small finds 0.71 of the reworded questions alone and 0.48 inside Memo 0.131.50 (0.34 in 0.131.47), so most of the
loss is in how Memo ranks and merges results, not in the model. A larger model adds about 0.1 more.

EmbeddingGemma 300M is the best of the five here: 0.94 of the reworded questions in other words at @10, above
e5-large (0.82) and above every hosted engine in section 2 (Supermemory 0.88, Honcho 0.76), with no model call at
write time and nothing leaving the machine. It indexes 5 times slower than e5-small and 2.7 times faster than
e5-large. Its licence is the Gemma Terms of Use, not MIT, so the owner accepts them when downloading it.

EmbeddingGemma cannot be tested inside Memo: memo downloads it but embeds notes and mail only with e5-small
(BUG-574 in the session journal; a fix with a model setting and three sizes is in progress).

With Memo 0.131.47, OpenClaw + WireCat's two misses and Hermes + WireCat's three (q20, q21, q22) were all "relative date" questions ("hold it 9 days from today"): memo 0.131.47
dates an imported note by the import moment, not by its file's time, so the agent counted from 7 November. Memo 0.131.50 (cli-core 0.604.0) dates a note by its file and also
carries the colon and ranking fixes; with fresh stores both WireCat agents answer every relative date question.
Hermes + WireCat's one miss is q44, the right answer with the replaced value in brackets. Supermemory's agents read only its memories, which lost most facts; its search over documents scored
0.91 at @10 (section 2), which the agents never see.

Hindsight's first runs never reached the memory, and both scored 4 of 50 by answering "unknown". Hermes pins
hindsight-client 0.6.1 and read the installed 1.2.0 as missing, so every recall failed (it also installed 0.6.1 into
its own Python, SEC-152 in the session journal; the runner now forbids that). OpenClaw's Hindsight plugin refuses its
tools in a session without a message provider, which `openclaw agent --local` has none of; the runner now names one
in the session key. The rows above are the second runs. In OpenClaw 25 of the tool calls still failed with
"Hindsight client is not initialized" (the first call can come before the plugin's client starts); the agent then
tried another of its three tools. Hermes's recall shows the facts without the record name, so it rarely cites one.

Honcho's conclusions carry no record name, so its agents could cite a source only for the "unknown" questions.

Key fix (7 November): every agent first "missed" the same two questions, q34 (which venue is booked) and q35 (how
many times the drill moved). The answers were right; the key was wrong. The generator tells each story's twin about
a random other project, and that was sometimes a project the same kind of question asks about, so two stories
shared a subject. The records stay as published (stores hold them); the keys of q34 and q35 are now read off both
stories, q01, q02 and q22 gain the twin's value as a stale answer, and the generator fails if this happens again
without a fix. All runs above are scored with the fixed key. Run records: [runs/v3-2026-11-07](runs/v3-2026-11-07).
